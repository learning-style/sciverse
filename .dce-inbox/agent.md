### 0.0. Ship the reasonable recommendation 

**When two defensible designs are in front of you, pick the better one, build it, and say what you picked — do not stop the cycle to ask which.** Circle back if it turns out wrong; that is what `<deferred_activity>` and the sprint plan are for.

 Equivocation is the expensive outcome: two good options and no decision ships nothing, while either option shipped leaves the other one available next cycle. This does not license skipping a **genuine** approval — a spend, a deploy, a destructive act, anything the curator has ruled on before (§4.1's approval grammar exists for those). It retires the habit of asking permission to choose between two implementations.

### 0.0.1. When you fan work out, five is the default 

**Whenever subagents or parallel tool calls are the right tool, run 5 at a time unless you have a reason to say otherwise.** Not two, not "one at a time to be safe", and not "as many as I can spawn" — five, and say in `<course_of_action>` when you chose differently and why.

 The number exists because a shared machine has two big lanes and a small one; five keeps a second caller alive while you work. Refusing to parallelize at all is the more common failure: a task that is genuinely N independent reads should be N workers, not N sequential turns in your own context.

## 2. Source-of-truth doctrine

DCE artifacts under `src/Artifacts/A*.md` are the **absolute source of truth** for the project. Three rules govern them:

1. **Code follows documentation.** If the code deviates from an artifact, update the artifact *first* to reflect the new intended reality, then change the code.
2. **Artifact-first edits.** When implementing a new feature or refactor, edit the relevant planning artifacts (or create new ones) before touching code.
3. **Resolve drift explicitly.** If an artifact conflicts with the code on a point you touch, correct the artifact and note the correction in your `<summary>`.

### 2.1. The artifact mandate — one feature, one artifact home

Rule 2 said "artifact-first"; this section makes the **unit** binding. It exists because C30 shipped an entire feature (the Code Cosmos) whose only documentation was a header comment in its own `.tsx` file — the curator caught it: *"we want a separate artifact all together for any such feature."*

- **Feature-class work requires a dedicated artifact.** Before code lands for a new user-facing capability, subsystem, or load-bearing code file, a dedicated `A*.md` (or a dedicated, versioned section of the owning feature artifact) must describe it: intent, design, contracts, verification. A header comment in the code file does NOT count — comments travel with the file; artifacts are the project's memory.
- **The two-reference floor.** A new code file is creatable only when at least **two** artifact references name it: (1) its design home (the owning feature artifact) and (2) the living roadmap/sprint artifact's cycle sweep. A file-structure artifact whose job is to list all files by name counts for neither.
- **The retro-artifact rule.** Whenever a feature is identified that has no artifact — in any cycle, by agent or curator — authoring the missing artifact becomes part of **that cycle's scope**, not a deferral candidate. An undocumented feature is drift (rule 3), and drift resolves in the cycle that finds it.
- **Self-check before the deliverable:** for every code file this cycle CREATED, name its two references in `<course_of_action>`. Can't name them → write the artifact before writing the deliverable.

Witnessed case: C30's Code Cosmos → back-filled as A434 in C31, the mandate's first act of compliance.

The artifact hierarchy that matters most:
- **A52.1 — Parser Logic and AI Guidance** — parser rules for AI Studio responses; does not apply to you but is referenced by A52.2.
- **A52.2 — Interaction Schema Source (manual)** — the schema injected into `prompt.md` for AI Studio. Do not apply A52.2's `<file path="…">…</file_artifact>` output convention; that is the manual path's serialization. Your path uses direct tool calls.
- **A52.4 — Auto-Documentation Logic** — if referenced by cycle context, honor its guidance on where to drop auto-generated docs.
- **A411 / A411.1 / A411.2 / A414** — the Ascentia / agent.md / Verbosity Toggle family. A411.3 (this file) is inside it.

### 2.2. Internal provenance is tagged, not scattered 

This schema is read in two places: **inside the DCE's own repo**, where a citation like "the C105 ruling" or "A419 §4" is a real address the reader can open — and **inside every other workspace**, where the same citation names an artifact that does not exist and a cycle number that belongs to a different project's history. 

So provenance is **tagged**, and the generator strips the tagged text from every brief whose workspace is not the DCE itself:

| Tag | Shape | Use for |
|---|---|---|
| `` | block | a whole paragraph / table / example that only means something at home |
| `` | inline | a citation, a witnessed-case aside, a curator quote inside a sentence that must survive without it |

Two rules when you write in this file:

1. **The RULE goes outside the tag; the PROVENANCE goes inside.** A stripped brief must still read as a complete instruction — never put the imperative inside the tag and leave only the citation.
2. **Cycle numbers and `A###` references always go inside a tag** unless the surrounding sentence is itself internal-only. The same applies to file paths under `src/Artifacts/`, `dce.db`, and any DCE-only script name (those also have the older `DCE-REPO-ONLY` block form, which the generator strips the same way).

 "reproduce": "the steps", "expected": "…", "actual": "…",
 "includeCycleContext": false, // opt-in ONLY, and only when they ask

```

The DCE consumes it within ~1s, **attaches the telemetry itself** (build, license tier, harness and its gates, orb + cycle, every live session, the recent error tail) and posts it through the same `/feedback` door the button uses. Do NOT gather telemetry by hand, do not ask the curator for their version number, and never put file contents, transcripts or secrets in the block. A malformed drop is left in place with a warning rather than sent.

**The performance record.** The DCE quietly records how it is behaving: what each keystroke actually cost, the extension host's memory and stalls, every child process it started, and a trail of the DCE commands and errors around the moment. For a report about anything that felt SLOW, HUNG, FROZE, LAGGED, CRASHED or flashed a window, that record is usually the difference between an actionable report and a shrug. **Ask before you take it** — one plain sentence naming what it carries (timings, memory, the last few commands — none of their code, prose or files) — and set `"includePerf": true` only on a yes. On a no, or no answer, file the report without it. Never ask for a wording report, a feature request or an idea.

### 3.7. Borrow the vocabulary)

**When the cycle asks you to model, validate, exchange or display structured data, spend one search on the published vocabulary before you design a field.** Structured-data-shaped asks: a schema/type for a real-world thing · a validation or eligibility rule over one · an import/export/interop format · anything read by a machine you do not own.

1. **Does [schema.org](https://schema.org/docs/schemas.html) already name this thing?** (823 types — `Person`, `Organization`, `Place`, `Event`, `Product`/`Offer`, `CreativeWork`, `Review`, `Action`, the media objects.) If so, take its names and relationships even when you store the data your own way.
2. **Does the CONSUMER publish a profile of that type?** The vocabulary is the noun; the consumer's profile is the law. schema.org says what a `JobPosting` is — Google's profile says which properties are *required* for it to render at all, and which mismatches get you penalised. Read both.
3. **Only then extend.** Local needs become extra properties beside the borrowed ones, never renames of ones that already exist.

Record the choice with the A499 §4 template in the artifact that owns the feature, and serialize as JSON-LD (`"@context": "https://schema.org"`). Skip all of this for internal-only shapes with no external reader (cache rows, UI props, IPC payloads), and never contort real data into a type that does not mean what you mean — say so in one line and diverge deliberately.

Curator, C122: *"there's no way that we can be the only idiots who can't get, if X is farther than Y, disqualify, correct … we need a DCE artifact, like a template that contains that."* The rule generalizes the move that worked: stop deriving, go read the manual.

### 3.8. Name the relationship before you draw)

§3.7 for pictures. Same failure, same cure: the world already named the thing, and an agent that invents its own shape is strictly worse off than one that goes and reads the catalogue.

**When the cycle asks you to draw something a reader is meant to READ rather than admire, name the relationship before you choose a chart.** Diagram-shaped asks: a chart of some numbers · a flow, funnel or pipeline · an architecture or system picture · a comparison · a dashboard tile · anything whose job is to make a number legible.

1. **Which of the nine relationships is it?** — deviation · correlation · ranking · distribution · change over time · magnitude · part-to-whole · spatial · **flow**. Write the word down before you choose a chart. *Most bad charts are a correct picture of the wrong relationship* — a funnel drawn as counts is a flow drawn as magnitude, and the drop-off, which is the whole question, becomes invisible.
2. **Take the type the vocabulary already names for it.** The [FT Visual Vocabulary](https://github.com/Financial-Times/chart-doctor/tree/main/visual-vocabulary) is the one to reach for first because it is *organised by relationship*, not by picture. [The Data Visualisation Catalogue](https://datavizcatalogue.com/) has the anatomy and the when-NOT-to-use; [From Data to Viz](https://www.data-to-viz.com/) is the one to use when the shape of your data is the constraint. Use the published name in the code and the artifact, and keep the colloquial alias — "alluvial (a Sankey)" — because the alias is what anyone will search for.
3. **Read the caveats before you commit.** Every catalogue publishes when a type FAILS. A type chosen without reading its failure mode is a type you will redraw.
4. **Only then extend.** A local need is a variation on a named type, never a new unnamed picture. If you genuinely diverge, say so in one line and say from what.

Record the choice with the A502 §4 template in the artifact that owns the feature. **A502 chooses the chart; the `dataviz` skill draws it** (palette, contrast, marks, legends, axes, interaction) — they compose, in that order, and neither replaces the other.

**Skip all of this** for pure ornament (an orb, a logo, a background) and for a one-off diagram with a single reader. Never contort real data into a type that means something it does not — say so and pick again.

## 4. The structured response (what you write to the deliverable file)

You write three XML-tagged prose sections to a deliverable file in **`.dce-inbox/`**. The filename depends on cycle phase (§0.1):

- **Planning phase:** `.dce-inbox/agent-response-r{N}.md` where `{N}` is your response slot index (1-based, named in `<Cycle Context>`'s `<response_slot>` tag if present, else default to `1`).

The DCE parser reads these files and renders them in the PCPP response tab. Markdown inside the tags is preserved by the parser. Always **overwrite**, never append (each cycle gets a fresh deliverable file).

### 4.1. Required structure
```markdown

</summary>

<course_of_action>
[What you actually did, in bulleted order. Each bullet: action + file reference + trigger/reason. No rationale paragraphs.]
</course_of_action>

<curator_activity>
Imperative bullets, one sandbox-impossible action per line. NEVER list CLI commands (git / npm / node / curl / build / test / package). The agent runs those directly via Bash. NEVER list git commits — see §5.2. INSTRUCTION-COMPLETENESS: every bullet must be executable as written by someone who was not in this session — either the bullet carries every step in plain sentences (where to click, what to look for, what done looks like), or it is one imperative line + a markdown link to the artifact SECTION holding the full steps ("— full steps: [A438 §5"), written first if it doesn't exist. ## 5. Commit discipline

### 5.1. Cadence (the baseline-and-review contract)
Exactly one commit per cycle, **at the START of the cycle**, capturing the previous cycle's surviving edits. The cycle's own work stacks on top as uncommitted changes; the curator reviews them in DCE's UI; the *next* cycle's start either commits the survivors or the curator has already re-baselined them away. This means:

- Cycle N's first action (after reading the prompt) is `git add` + `git commit` of cycle N−1's leftover work, message `DCE Cycle <N−1>: <headline>`.
- Cycle N's last action is leaving the working tree dirty so the curator can review.
- Multiple commits *within* a cycle are allowed only when the curator explicitly asks for a mid-cycle checkpoint. The default is one-commit-per-cycle, at the start.

### 5.2. Never tell the curator to commit
The curator does not run `git` themselves. `<curator_activity>` blocks **must not** contain `git add`, `git commit`, `git push`, `git tag`, or any other git CLI invocation. If the agent realizes a commit is needed, the agent runs it directly via Bash; the curator hears about it as past-tense factual reporting in `<summary>` or `<course_of_action>` (e.g., *"Committed prior cycle's work as `637b5f0`"*), never as a future-tense instruction in `<curator_activity>`.

This is the same rule as the broader "agent runs all terminal commands" doctrine, but called out separately because git commits are the most common violation surface and the curator's UI flow depends on it.

### 5.3. Message format
```
DCE Cycle <N>: <headline clause>
- bullet
- bullet
```
Mirror the A52.2 rule #12 preference for terse factual commits.

### 5.4. Never
- `git commit --amend` (the curator reads history).
- `git push --force` (the curator pushes when ready).
- `git commit --no-verify` (if a hook fails, fix the underlying issue).

## 7. Error handling

If a step fails (build, test, commit hook):
1. Read the error output.
2. Investigate the root cause — do not retry blindly and do not bypass with `--no-verify` or `--force`.
3. Fix the underlying issue, then re-run.
4. If the cause is the cycle's ambiguity rather than a bug (e.g., a curator-stated fact that the code contradicts), surface the conflict in `<summary>` + `<curator_activity>` and continue with what you can do.

### 7.1. Bug-cycle investigation discipline

When a cycle's ask is a BUG (a reported failure, an unknown cause):
1. **Reproduce first** — run the failing case and read the actual output before forming a hypothesis.
2. **Hold ≥3 competing hypotheses** before chasing any one; the loudest signal in the logs is one hypothesis, not the conclusion.
3. **Gather evidence per hypothesis** by reading the code paths end to end; let evidence kill hypotheses (a hypothesis you can't test is a guess).
4. **Trace the full causal chain** — a fix that silences the symptom without removing the defect leaves it latent.
5. **Verify before AND after** — confirm the cause with evidence before editing; demonstrate the failure mode is gone after.
6. **Report the rejected hypotheses** in `<course_of_action>` (one clause each) — the curator learns as much from what it wasn't.

### 7.2. Permission-block protocol

Some harnesses run the agent under a permission system whose AUTO mode can deny a tool call **silently** — the classifier rejects it, the step is skipped, and the cycle's output quietly loses a piece. When the DCE generates this brief for such a harness, it appends a **harness-matched protocol block** at the end of M3 (same append mechanism as the verbosity directive — the artifact text here is the canon; the injected copy names the active harness's ask channel):

- **If any tool call is denied** by the permission system or an auto-mode classifier, do NOT silently skip it and do NOT work around it.
- **Stop and ask the curator** through the harness's ask channel (e.g., Claude Code's `AskUserQuestion` tool, or a plain question ending the turn): state the exact command/edit that was denied and offer approve/deny.
- **On approval, retry** the action with that approval on record. **On a second denial**, report the block in `<curator_activity>` with the exact command so the curator can run it themselves or flip the permission mode.
- A silently skipped step is a defect; an asked question is not.

History: the curator hand-pasted this protocol into a C56/C57 cycle context to test it, then ruled: *"you should make it part of the interaction schema when that harness is chosen."* The C56 interim home (appended to the claude-code bootstrap prompt) is retired — the bootstrap stays lean; the schema carries the contract.

**C80 addendum (docs-grounded, A475 §8):** under Claude Code's `dontAsk` and `bypassPermissions` modes the `AskUserQuestion` tool is ITSELF denied — the ask channel named above does not exist there. In those modes the protocol degrades one rung: state the denied call and the question as plain prose ending your turn, and always mirror the block into `<curator_activity>` with the exact command. The instrument (a visible gap + a visible question) matters more than which channel carries it.

### 7.3. Terminal & long-run doctrine

Some harness models **delegate terminal commands to the human** — witnessed C107 (towerdefense ss4): Antigravity's model told the curator to run `npm run dev` themselves, and the curator's annotation *"i don't run terminal commands, you do"* didn't take. The doctrine that corrects it is **schema canon, harness-matched into M3** exactly like §7.2 (the injected copy may name harness-specific mechanics):

- **You have a working shell tool — run every terminal command yourself** (npm / node / git / build / test) and NEVER hand a CLI command to the curator; they do not run terminals (§5.2, §8, `feedback_agent_runs_terminals.md`).
- **Long-running processes (dev servers like `npm run dev`) — use the harness's own background lane; the recipe is harness-specific.** Under **Antigravity**, `Start-Process`/`nohup` detaches DO NOT survive: `run_command` reaps each command's whole process tree at completion (kill-on-close job semantics — probed C109: a `Start-Process`-detached ping was already dead when the NEXT tool call looked for it, while the identical recipe outside agy survives). Instead run the dev server as a **plain foreground command** (`npm run dev`) — agy's `WaitMsBeforeAsync` moves it to a managed background task that outlives both the command and the session (probed C109: the towerdefense vite started this way at 13:28 still served HTTP 200 five hours after its session died). Under **claude-cli and shell-native harnesses**, foreground blocks the tool — there the OS detach IS the lane (Windows: `powershell -Command "Start-Process cmd -ArgumentList '/c','npm','run','dev' -WindowStyle Hidden"`; POSIX: `nohup npm run dev >/tmp/dev.log 2>&1 &`), or the runtime's own `run_in_background` when it has one.
- **Windows PowerShell `>` redirection writes UTF-16LE** — a log file created that way is unreadable by agy's file reader (`unsupported mime type text/plain; charset=utf-16le`, the C108 wedge). Don't verify a server by tailing a redirected log; **probe the port** (`curl` the URL) and report the URL. The curator's only action is opening the browser.

History — the same migration as §7.2, one lesson later: C56 (`0b6b60f`) put the permission protocol on the claude-code bootstrap; C57 (`5e2aa72`) moved it into the schema after the curator's ruling. C107 (`9090eb6`) put THIS doctrine on the antigravity bootstrap ("the doctrine rides the bootstrap now"); the curator caught the repeat: *"i still see the shoddy placement of the 'terminal doctrine' language placed into the bootstrap … that needs to go into the antigravity-shaped/specific interaction schema."* The bootstrap stays lean (path + context-budget mantra only); the schema carries every behavioral contract. `buildTerminalDoctrine` in `prompt.service.ts` is the injector; Antigravity is its first harness match, and any future harness whose model exhibits the delegate-to-human pattern joins the switch, not the bootstrap. The C107 recipe itself was also WRONG for agy (it prescribed the impossible `Start-Process` detach — the exact cause of the C109 "47 streaming calls for `npm run dev`" carousel: eleven detach variants that can never survive, each probed dead); the C109 probe-grounded text above replaces it.

## P2.2. The suite (verbatim from A475 §2)

```

permission-test-results.md at the repo root. Perform each numbered step IN ORDER;
after EACH step append exactly one line "N. <tool> OK — <one clause>" to

1. Read: read the repo's largest source file and name it.
2. Glob: count the files matching **/*.{js,ts,html} and report the count.

4. Write: create scratch/perm-probe.txt containing the current step list.
5. Edit: change "perm-probe" to "perm-probe-edited" inside scratch/perm-probe.txt.
6. Bash (read): run `git status --short` and report how many lines it printed.
7. Bash (write): run `git add -N scratch/perm-probe.txt` then `git reset scratch/perm-probe.txt`.
8. Bash (network): run `curl -sI https://example.com | head -3` and report the HTTP status line.
9. WebSearch: search the web for "VS Code extension marketplace publishing" and name one result title.
10. WebFetch: fetch https://example.com and report its <title>.
11. TodoWrite: create a 3-item todo list for this test and mark all three complete.
12. Bash (long-running): run a command that sleeps 70 seconds, then echoes DONE

## 2. Tactical tracing
When behavior is wrong, log/inspect **every hop of the data's journey** and find the hop where it breaks:
`input captured → sent → received → transformed → persisted → displayed`. One tagged log per hop (`[Component] sending: …`) pinpoints the failing link in minutes. The same applies to documents: trace a claim from source → notes → draft → citation.

## 3. A-B-C isolation (for resistant bugs)
When repeated small fixes on the real component fail:
1. **Preserve the original** as the control — never debug by deleting.
2. Build 2-3 **minimal parallel test cases**, each changing ONE variable (raw handler vs. state-driven vs. prop-driven; or template X vs. Y).
3. Run them side by side; whichever succeeds names the failing pattern.
4. Codify the finding (a case study — T8), port the winning pattern into the original, delete the test harness.

## 4. Hard rules
- Reproduce before fixing; verify after fixing (before/after evidence).
- Never retry the identical failing action more than twice — change the approach or report the actual error.

## How to keep this codex (rules for the agent)

1. **Only the user authors content.** Every entry is a VERBATIM quote from a cycle context, stamped with its cycle number. Never paraphrase, never "clean up," never delete.
2. **Route, don't rewrite.** When a new cycle's words touch an existing topic, add them to that topic's chapter — **at the TOP: chapters read newest-first, sorted on the entry's date stamp** (A468 §9.9 — the user can wipe cycles and restart at "cycle 1", so the cycle number is not a stable sort key; the date is). New topic → new chapter.
3. **Supersession is quoted, never judged.** If the user's own later words retire an earlier idea ("forget X — do Y"), mark the earlier quote ~~struck~~ and cite the cycle of the striking quote. The struck text stays readable.
4. **Chapters share the cycle-notes key grammar** (`category: topic`), with an optional subcategory (`category/subcategory: topic`) when the user's own words draw a finer line (A468 §9.3). Every cycle-note key is also a codex chapter pointer.
5. **Read before you build.** Before changing a feature's spec or code, read that feature's chapter — drift between what the user SAID and what the system IS must surface, not accumulate.
6. **Chapters lead with their consequences (A468 §9.1).** Every chapter opens with a `**Made real by:**` line — the code files and spec artifacts that exist BECAUSE of its words (the agent maintains this line; it is routing metadata, not user content). `— (not yet built)` is an honest drift marker, never an omission.
7. **Entries are stamped (A468 §9.2, + date C100):** `— C<n> · ◈ <orb> · v<version> · <YYYY-MM-DD>` — cycle, the orb the words arrived through, the product version current when spoken (omit when the project has none), and the DATE the words were spoken (the sort key — §9.9). Quotes carry stable numbers (`K<chapter>.<n>`) so anything can cite (`per K2.3`) instead of re-emitting.
8. **K-numbers never renumber (A468 §9.4).** Chapters that prove to be one feature MERGE: the survivor absorbs the other's entries as whole numbered blocks, and the index keeps a tombstone (`K5 → merged into K4, C<n>`) so old citations still resolve. Moving lines = moving numbered blocks verbatim.
9. **One codex, many orbs (A468 §9.5).** Every orb's cycles route into this one file; the ◈ stamp keeps parallel chains distinguishable — the codex is where the chains see each other.

# Welcome!

You have successfully initialized the **Data Curation Environment (DCE)**.

This folder (`src/Artifacts`) is the "long-term memory" for your project. The files here are **Artifacts** — living documents that define your project's vision, architecture, and plans. Your agent reads them every cycle and updates them as the project evolves; they are the source of truth the code follows.

## How the DCE works

Work happens in **cycles**. Each cycle you write what you want in the **Cycle Context**, click **Activate Agent**, and the DCE:

1. **Baselines** — commits the previous cycle's surviving work so the new cycle's changes are reviewable as clean git colors.
2. **Generates `agent.md`** — the full cycle context (history, project scope, your selected files) for your agent to read top-down.
3. **Activates your harness** — hands the cycle to the agent you picked with the plug button (see below).
4. **Ingests the response** — when the agent finishes, its structured summary appears in the cycle's response tab automatically.

You review the uncommitted changes (the git colors ARE the review UI), then write the next cycle.

## Next Steps

### 1. Review the Generated Artifacts
The agent generated a set of starter artifacts for you (e.g., `A1. Project Vision`, `A3. Technical Scaffolding`). Open them to see the plan — and edit them; they steer every future cycle.

### 2. Pick your Agent Harness (the plug button 🔌)
In the **DCE Parallel Co-Pilot** panel header:
*   **Claude Code** — Activate Agent opens a Claude Code tab pre-filled with the bootstrap; you press Enter. Model/thinking stay your choice.
*   **Hermes (embedded)** — runs inside the DCE's Cognitive Commons. Choose your connection:
    *   **Ascentia Cloud (managed)** — free tier; the DCE services the best model currently available. Sign in with GitHub in DCE Settings once — your key is fetched automatically.
    *   **Custom Endpoint** — point at your own OpenAI-compatible URL (vLLM, LM Studio, Ollama). The model is chosen automatically from what your endpoint serves.
*   **Clipboard** — copies the bootstrap for any other harness (Cursor, Codex, a terminal).

### 3. Run Cycle 1
You are now in **Cycle 1**. Describe what you want in the Cycle Context and click **Activate Agent (Cycle 1)**. Watch the agent work — Hermes streams into the Cognitive Commons Local panel; Claude Code runs in its own tab.

### 4. Git Repository Initialized
The DCE initialized a git repository and created a feature branch from your project scope (e.g., `feat/my-project-scope`).
*   **Action:** Click **"Publish to GitHub"** in the Onboarding view (optional) to publish the branch.

### 5. The "Baseline" Workflow
After a cycle completes, the changed files sit **uncommitted** for your review:
1.  **Review** the diffs (colored files in the tree; the diff viewer shows exactly what changed).
2.  **Test** the result.
3.  Start the next cycle — the DCE baselines (commits) the surviving work automatically at Activate-click. If something broke, **Restore Baseline** reverts to the last good state.
